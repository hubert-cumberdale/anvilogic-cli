# v0.3.0 adoption validation

Validation date: 2026-09-14

## Outcome

The private `v0.3.0` Alpha prerelease passes the consumer-side schema compatibility checks for the
committed minimal corpus. The downloaded release archives reconcile with their published hashes,
the released wheel emits the exact v1 schema bytes, every corpus record validates, and the fixture
manifest reconciles with the deterministic JSONL artifact.

This is compatibility evidence, not full source-fidelity certification. No representative
outside-Git export was available in the validation environment, so preservation of shapes from a
specific tenant export could not be independently checked. The fixture was constructed from the
target structural profile described below and contains only synthetic data.

No version, release, source schema, external repository, or tenant state was changed. The release
remains an Alpha prerelease and was not promoted to stable.

## Fixture hygiene and profile

The committed fixture uses only synthetic scenario, stage, identifier, rule, title, description,
and behavioral-intent values. Its sole reference uses `example.com`. It contains no raw response
envelopes, owners, rule logic, credentials, private hosts, or tenant prose. The repository
public-safety scan passed with the fixture and this report present.

The original export was not present, so no raw records were read or transformed during this run.
An eventual source-fidelity check must keep its run directory at `0700`, its files at `0600`, and
outside Git. Only a reviewed sanitized derivative may replace or extend the committed fixture.

The two-record corpus deliberately retains this representative structural profile:

- one three-stage scenario and one scenario with an empty stage list;
- stage membership cardinalities of two, one, and zero;
- one identifier repeated across two stages;
- both technique `T1003` and sub-technique `T1059.001` forms;
- populated platform and tactic metadata alongside empty platform, tactic, reference, and rule-ID
  arrays.

## Compatibility method

`tests/test_v030_adoption.py` is intentionally independent of exporter normalization. It loads
`threat_scenario_record.schema.json` through Python package resources, opens the JSONL artifact as
a binary stream, decodes and validates one record at a time, and uses a direct JSON Schema
2020-12 validator.

The test also recalculates schema and artifact hashes, derives counts from the records, and proves
that the JSONL bytes are compact, key-sorted UTF-8 with exactly one LF-terminated object per line.
Separate mutations reconfirm that the released schema rejects missing required fields, mistyped
fields, additional fields, and malformed nested fields.

## Limitations

- Source-to-fixture cardinality and field-preservation checks remain pending until an existing
  normalized export is supplied outside Git with the required private permissions.
- The corpus exercises selected compatibility boundaries; it is not an exhaustive sample of all
  possible v1 records.
- JSON Schema validation proves record-shape compatibility, not the quality or completeness of a
  future collection from a tenant.
- No tenant calls, live authentication, mutation paths, PyPI publication, stable-release
  promotion, or AttackIQ changes were performed.
